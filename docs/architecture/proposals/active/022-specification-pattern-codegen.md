# PROP-022: Specification Pattern with Code Generation

**Status:** idea  
**Size:** medium  
**Created:** 2026-06-17  

## Problem / Motivation

Business rule validation logic currently lives as inline lambdas at the call site:

```csharp
order.EnsureBusinessRule(o => o.Amount is > 0 and <= 10_000, new OrderAmountValid());
```

This works for simple cases but has three structural problems.

**Not reusable.** The same predicate is duplicated wherever the rule must be
checked. There is no single place that owns the logic for what it means to satisfy
`OrderAmountValid`. If the threshold changes, every call site must be updated manually.

**Not composable.** Combining multiple rule checks requires chaining `ResultExtensions`
calls procedurally. There is no first-class construct for expressing "all of these
conditions must hold" as a single named thing that can be passed around, stored, or
tested in isolation.

**Not independently testable.** The predicate is anonymous — there is no type to
instantiate in a test, no clear contract to assert against. Testing the validation
logic means testing it indirectly through a method that happens to call it.

The Specification pattern (Evans, Fowler) solves all three: it reifies predicates
into named, composable, testable objects. Wiring that to the existing BusinessRules
framework via a new attribute and a source generator gives users a structured,
traceable path from rule definition to validation logic with minimal boilerplate.

## Sketch

### Package structure

Two new packages, following the existing bridge pattern:

| Package | Responsibility | BusinessRules dep |
|---------|---------------|:-----------------:|
| `MaVe.Specifications` | Core `ISpecification<T>`, `Specification<T>` base, `And`/`Or`/`Not` combinators | None |
| `MaVe.BusinessRules.Specifications` | `[BusinessRuleSpecification]` attribute, source generator, `Result<T>` bridge | Yes |

`MaVe.Specifications` is independently consumable — no coupling to BusinessRules.
The bridge package adds the generator and attribute that connect the two systems.

### `MaVe.Specifications` — core types

```csharp
public interface ISpecification<T>
{
    bool IsSatisfiedBy(T candidate);

    ISpecification<T> And(ISpecification<T> other);
    ISpecification<T> Or(ISpecification<T> other);
    ISpecification<T> Not();
}

public abstract class Specification<T> : ISpecification<T>
{
    public abstract bool IsSatisfiedBy(T candidate);

    public ISpecification<T> And(ISpecification<T> other)
        => new AndSpecification<T>(this, other);

    public ISpecification<T> Or(ISpecification<T> other)
        => new OrSpecification<T>(this, other);

    public ISpecification<T> Not()
        => new NotSpecification<T>(this);
}
```

The combinator implementations (`AndSpecification<T>`, `OrSpecification<T>`,
`NotSpecification<T>`) are internal to the package — callers only interact via
`ISpecification<T>`.

### `[BusinessRuleSpecification]` attribute

Defined in `MaVe.BusinessRules.Specifications`. Decorates a `Specification<T>` class
to bind it to a rule key:

```csharp
[AttributeUsage(AttributeTargets.Class)]
public sealed class BusinessRuleSpecificationAttribute(string ruleKey) : Attribute
{
    public string RuleKey { get; } = ruleKey;
}
```

### User-authored specification

The user writes a regular C# class with full IDE support — IntelliSense, refactoring,
go-to-definition, debugger stepping all work normally:

```csharp
[BusinessRuleSpecification(OrderAmountValid.Key)]
public class OrderAmountValidSpec : Specification<Order>
{
    public override bool IsSatisfiedBy(Order candidate)
        => candidate.Amount is > 0 and <= 10_000;
}
```

Using the generated `const string Key` from the rule class as the attribute argument
keeps the binding refactor-safe: renaming the constant will surface a compile error
rather than silently drift.

### Source generator output

The generator — part of `MaVe.BusinessRules.Specifications` — detects classes
decorated with `[BusinessRuleSpecification]`, resolves the rule class name from the
JSON (same `AdditionalTexts` pipeline as the existing generator), and emits a static
helper class per specification:

```csharp
// <auto-generated />
using MaVe.BusinessRules;
using MaVe.BusinessRules.ResultExtensions;
using MaVe.Monads;
using MyApp.BusinessRules.Rules.Orders;

namespace MyApp.BusinessRules.Specifications.Orders;

public static class OrderAmountValidValidation
{
    /// <summary>The specification instance used to evaluate OrderAmountValid.</summary>
    public static readonly ISpecification<Order> Specification = new OrderAmountValidSpec();

    /// <summary>
    /// Validates <paramref name="candidate"/> against OrderAmountValid.
    /// Returns a successful Result if the specification is satisfied, a failed Result otherwise.
    /// </summary>
    [ImplementsBusinessRule(OrderAmountValid.Key)]
    public static Result<Order> Validate(Order candidate)
        => Specification.IsSatisfiedBy(candidate)
            ? Result.Success(candidate)
            : OrderAmountValid.ToException().ToResult<Order>();
}
```

The emitted `[ImplementsBusinessRule]` on `Validate` satisfies the existing BR002
analyzer check automatically — no manual attribute placement needed.

### Analyzer extension: BR005

A new diagnostic to validate `[BusinessRuleSpecification]` attribute arguments,
following the same pattern as BR001:

| Diagnostic | Severity | Trigger |
|------------|----------|---------|
| `BR005` | Error | `[BusinessRuleSpecification(key)]` references a key that does not exist in any `*.BusinessRules.json` |

This closes the gap at the attribute level in the same way BR001 closes it for
`[BusinessRule]` and `[ImplementsBusinessRule]`.

### End-to-end developer experience

**Step 1: Define the rule (unchanged)**

```json
{
  "ClassName": "OrderAmountValid",
  "Key": "ORD-001",
  "Requirement": "Order amount must be between 1 and 10,000",
  "Category": "Orders"
}
```

**Step 2: Write the specification**

```csharp
[BusinessRuleSpecification(OrderAmountValid.Key)]
public class OrderAmountValidSpec : Specification<Order>
{
    public override bool IsSatisfiedBy(Order candidate)
        => candidate.Amount is > 0 and <= 10_000;
}
```

**Step 3: Use it**

```csharp
// Direct check
bool valid = new OrderAmountValidSpec().IsSatisfiedBy(order);

// Generated Result<T> bridge — no boilerplate
Result<Order> result = OrderAmountValidValidation.Validate(order);

// Composition — untracked composite, no rule key needed
ISpecification<Order> canProcess = new OrderAmountValidSpec()
    .And(new OrderHasItemsSpec())
    .And(new CustomerIsActiveSpec());

if (canProcess.IsSatisfiedBy(order)) { ... }
```

**Step 4: Test in isolation**

```csharp
[Test]
public void IsSatisfiedBy_WhenAmountIsZero_ReturnsFalse()
{
    var spec = new OrderAmountValidSpec();
    var order = new Order { Amount = 0m };

    spec.IsSatisfiedBy(order).Should().BeFalse();
}
```

### Composites and traceability

Composite specifications created via `And`/`Or`/`Not` are intentionally anonymous —
they carry no rule key. This is correct: a composition of two rules is not itself a
declared business rule unless it is explicitly named and added to the JSON. Forcing
composites through the key system would create implicit rules with no traceability.

If a composite represents a meaningful domain invariant, the right path is to declare
a new rule key and write a new specification that expresses the composed condition
directly in `IsSatisfiedBy`.

## Open Questions

- **Generator coordination** — the new generator needs the key→className mapping from
  the JSON, same as `BusinessRulesGenerator`. Should both generators read
  `AdditionalTexts` independently, or should there be a shared utility? Shared utility
  would require a common `netstandard2.0` library, adding a dependency. Independent
  reads are simpler but duplicate the JSON parsing logic.
- **`[BusinessRuleSpecification]` vs `[ImplementsBusinessRule]`** — can
  `[BusinessRuleSpecification]` fully replace `[ImplementsBusinessRule]` as a way to
  satisfy BR002, or should both remain valid satisfiers? Replacing would be cleaner but
  is a breaking change for users already using `[ImplementsBusinessRule]` on hand-written
  validators.
- **Multiple specs per key** — should a second `[BusinessRuleSpecification("ORD-001")]`
  on a different class be an error (a key has exactly one canonical spec), a warning,
  or silently allowed? Multiple specs for the same key implies disagreement about what
  the rule means.
- **Spec class constructor parameters** — `Specification<T>` assumes a parameterless
  constructor for the generated `Specification` field. What is the right design for
  specs that require configuration (e.g., a threshold injected at construction time)?
  Static `Instance` is not viable. The generated `Validate` method could accept the
  spec as a parameter, but that moves instantiation back to the call site.
- **PROP-020 integration** — if PROP-020 ships first, should `Validate` accept the
  violation context from the spec? The spec could optionally override a method
  returning `IDictionary<string, object?>`, which the generator then passes through
  to the parameterized `ToException` overload.

## Prior Art / References

- Evans, *Domain-Driven Design* (2003), Chapter 9 — original formulation of the
  Specification pattern in a domain model context
- Fowler, [*Specifications*](https://martinfowler.com/apsupp/spec.pdf) (1997) — the
  paper that named and formalised the pattern
- [Ardalis.Specification](https://github.com/ardalis/Specification) — well-adopted
  .NET implementation; demonstrates the interface surface and combinator design
- [FluentValidation](https://docs.fluentvalidation.net/) — comparison point: richer
  validation with message context, but tightly coupled to its own runner model rather
  than composable predicates
