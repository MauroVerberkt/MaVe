# PROP-017: Ways of Working Docs in Docusaurus

**Status:** ready  
**Size:** small  
**Created:** 2026-06-02  

## Problem / Motivation

Process knowledge is scattered across multiple files — `CONTRIBUTING.md`,
`RELEASE-FLOW.md`, workflow YMLs, build scripts, and per-project `version.json`
files. Someone wanting to understand *how* the project operates needs to piece
things together from 10+ sources.

`CONTRIBUTING.md` serves as a quick-start but intentionally stays concise.
There is no rendered, cross-linked, deep-dive reference for:

- How CI jobs relate to each other and when they run
- The full versioning story (Nerdbank.GitVersioning, path filters, prerelease vs stable)
- The release ceremony end-to-end
- Why conventions exist (with links back to relevant ADRs)

This belongs in the Docusaurus site — same audience as Architecture
(contributors/maintainer), just focused on *process* rather than *design*.

## Sketch

### Location and Navigation

Add a **collapsed-by-default** "Ways of Working" category to the Architecture
sidebar, after the existing Design category:

```ts
// sidebarsArchitecture.ts
{
  type: 'category',
  label: 'Ways of Working',
  collapsed: true,
  items: [{type: 'autogenerated', dirName: 'ways-of-working'}],
},
```

New directory under `docs/architecture/`:

```
docs/architecture/
└── ways-of-working/
    ├── _category_.json
    ├── developer-setup.md
    ├── branching-and-prs.md
    ├── ci-pipeline.md
    ├── build-and-packaging.md
    ├── versioning-and-releases.md
    └── docs-deployment.md
```

### Page Outlines

**`developer-setup.md` — Developer Setup**

- Prerequisites: .NET SDK versions, Node.js, GitHub CLI, PowerShell 7+
- First-time clone walkthrough: `tools/setup.ps1` explained step-by-step
- Git hook configuration: what the `pre-push` hook enforces and how to debug it
  if it fires unexpectedly
- IDE recommendations and useful extensions
- Verifying a working setup: build, test, and docs site locally
- Source: `tools/setup.ps1`, `.githooks/pre-push`, `CONTRIBUTING.md`

**`ci-pipeline.md` — CI Pipeline Reference**

- Mermaid diagram: job dependency graph (`changes` → `build-and-test` →
  `publish-github-packages`; `changes` → `docs-validate`; all → `ci-gate`)
- Path filtering logic: which file changes trigger which jobs, and why
- `ci-gate` aggregation pattern explained: why one required status check beats
  many
- "CI is red — now what?" quick troubleshooting reference
- Source: `ci.yml`, `_build-and-test.yml`, `_docs-validate.yml`

**`branching-and-prs.md` — Branching and Pull Requests**

- Branch prefix table with the rationale behind each prefix
- `docs/` fast-track workflow: what `docs-push.ps1` automates and why
  docs-only PRs have a separate, lighter path
- Auto-merge mechanics and the `docs-only-guard` safety check
- PR lifecycle: create → `ci-gate` passes → squash merge → branch deleted
- Commit message format with scope conventions and examples
- Source: `CONTRIBUTING.md`, `docs-push.ps1`, `.githooks/pre-push`,
  `ci.yml` (`docs-only-guard` job)

**`build-and-packaging.md` — Build and Packaging**

- `Directory.Build.props` hierarchy: what each layer (root / src / tests) adds
- Per-layer additions: nullable annotations, XML doc generation, SourceLink,
  PublicApiAnalyzers, test framework references
- `.editorconfig` conventions: indentation, line endings, file encoding, and
  language-specific rules (see `.editorconfig` added in `chore/editorconfig`)
- Local pack scripts (`tools/build-*.ps1`) and when to use them vs CI
- Analyzer packaging model: why Roslyn components are packaged separately from
  library packages
- Source: `Directory.Build.props` (×3), `tools/build-*.ps1`, `.editorconfig`

**`versioning-and-releases.md` — Versioning and Releases**

- Nerdbank.GitVersioning overview: how `version.json` + git commit height
  produces the package version
- Per-project `pathFilters`: why independent version bumps per package require
  scoped change detection
- Prerelease flow: every merge to `main` publishes alpha packages to GitHub
  Packages
- Stable release flow: tag push → artifact-based version verification →
  NuGet.org
- Release operator checklist (expanded from `RELEASE-FLOW.md`)
- Source: `version.json` (×6), `release.yml`, `_publish-packages.yml`,
  `RELEASE-FLOW.md`

**`docs-deployment.md` — Docs Deployment**

- When docs deploy: only on pushes to `main` that touch `docs/**`
- Build pipeline: Node.js setup, `npm ci`, `npm run build`, GitHub Pages artifact
  upload
- GitHub Pages environment and the `pages: write` / `id-token: write` permission
  requirements
- How to test the docs build locally before pushing (`npm run build` in `docs/`)
- Relationship between `_docs-validate.yml` (CI validation on every PR) and
  `deploy-docs.yml` (deployment on merge)
- Source: `deploy-docs.yml`, `_docs-validate.yml`

### Relationship to CONTRIBUTING.md

`CONTRIBUTING.md` remains the canonical entry point — quick-start, actionable,
repo-root-discoverable on GitHub. No content is removed from it.

Add a single forward-reference line at the bottom of `CONTRIBUTING.md`:

> For detailed reference on the CI pipeline, versioning model, and release
> process, see the Ways of Working section in the documentation site.

The Docusaurus pages go deeper and add diagrams and cross-links. They do not
duplicate the quick-start content.

pages in the architecture overview index:


## Open Questions

All resolved:

1. **Developer Setup page** — Yes, add it as the first page in the section. Slightly
   verbose is fine; first-time setup friction is worth reducing.
2. **Docs deployment page** — Yes, document `deploy-docs.yml` as its own page. It is
   not too meta; understanding when and how the site publishes is useful
   operational knowledge.
3. **`.editorconfig`** — ✅ Done via `chore/editorconfig`. The
   `build-and-packaging.md` page will reference it.
